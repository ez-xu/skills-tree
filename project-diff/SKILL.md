# 工程代码对比技能

对比两个代码工程文件夹，智能识别源码与构建产物，生成功能级别的变更分析报告。

## 核心原则

- **智能识别**：不依赖硬编码的路径名，而是通过分析目录内容和文件类型来判断哪些是源码、哪些是构建产物
- **功能级别分析**：不只是列出文件差异，而是理解代码变更的意图和影响范围
- **记忆优化**：每次对比后，将项目的特定配置（源码路径、排除模式）保存到记忆中，下次对比同类项目时自动复用

## 执行流程

### 第一步：接收参数与初始分析

从用户输入中提取：
- `路径A` 和 `路径B`：两个要对比的文件夹路径
- 可选：用户指定的关注路径或排除路径

验证两个路径是否存在且为目录。

### 第二步：智能扫描目录结构

对每个目录执行 `scripts/scan_project.py` 脚本（或手动分析），获取目录结构概览：

```bash
python <skill-path>/scripts/scan_project.py <目录路径>
```

脚本会输出 JSON，包含：
- 顶层子目录列表（含文件数量统计）
- 文件类型分布（.c, .h, .py, .js 等）
- 可能的源码目录候选
- 可能的构建产物目录候选

**如果脚本不可用**，则手动执行以下分析：

1. 列出两个目录的顶层内容 `ls -la`
2. 对每个子目录，抽样检查其包含的文件类型
3. 根据以下启发式规则判断目录类型：

| 判断依据 | 判定为源码目录 | 判定为构建/排除目录 |
|---------|-------------|-----------------|
| 文件类型 | 包含 .c/.h/.cpp/.hpp/.py/.js/.ts/.rs/.go/.java 等源码文件 | 包含 .o/.obj/.elf/.bin/.hex/.exe/.dll/.so/.a/.map 等编译产物 |
| 目录名特征 | 通用源码名：src, lib, app, include, inc, components, modules, drivers, core | 构建相关：Debug, Release, Output, build, dist, out, target, bin, obj, __pycache__, node_modules |
| IDE/工具特征 | - | .git, .svn, .hg, .vscode, .settings, .idea, .eclipse, Brun |
| 配置文件特征 | - | .cproject, .project, .classpath, Makefile(仅当用户未要求关注时) |

**关键原则**：当不确定某个目录是否为源码时，**宁可保留**让用户看到，而不是排除掉。排除时向用户报告排除了什么以及原因。

### 第三步：获取差异文件列表

使用 `diff` 命令获取两个目录的差异概览：

```bash
diff -rq <路径A> <路径B> 2>/dev/null
```

输出示例：
```
Only in A/src/: file_x.c
Only in B/user/: new_feature.c
Files A/user/can0.c and B/user/can0.c differ
```

提取三类变更：
- **仅存在于A**：路径A有、B没有的文件
- **仅存在于B**：路径B有、A没有的文件
- **内容不同**：两边都有但内容不同的文件

### 第四步：Git 增强分析（可选）

检查两个目录是否都是 git 仓库：

```bash
git -C <路径A> rev-parse --git-dir 2>/dev/null && echo "IS_GIT_REPO"
```

如果都是 git 仓库，进一步检查是否同源：

```bash
# 检查是否有共同的 commit
git -C <路径A> merge-base $(git -C <路径A> rev-parse HEAD) $(git -C <路径B> rev-parse HEAD) 2>/dev/null
```

如果同源，使用 git 获取更丰富的变更信息：

```bash
# 获取两个版本之间的提交日志
git -C <路径B> log --oneline <共同祖先>..HEAD
# 获取具体的文件变更统计
git -C <路径B> diff --stat <共同祖先>..HEAD -- <源码路径列表>
# 获取带函数名的 diff
git -C <路径B> diff --function-context <共同祖先>..HEAD -- <源码路径列表>
```

如果不同源（独立 git 仓库），仍可用 `diff` 对比，并在报告中注明。

### 第五步：功能级变更分析

这是最核心的一步。基于 diff 输出，进行功能级别的分析：

1. **读取变更文件内容**：对每个有差异的源码文件，使用 Read 工具查看变更前后的关键部分

2. **识别变更模式**，从以下维度分析每个差异：
   - **新增功能**：新增的文件/函数/模块
   - **删除功能**：被删除的文件/函数/模块
   - **重构**：函数签名变更、逻辑重写但功能等价
   - **修复**：边界条件、错误处理、数值修正等小范围改动
   - **配置变更**：宏定义、常量、引脚配置、寄存器值等变更
   - **接口变更**：API 函数原型、数据结构、通信协议变更
   - **性能优化**：算法替换、缓存引入、中断处理改进

3. **提取函数名**：
   - C/C++：匹配 `^\w[\w\s\*]+[\s\*]+(\w+)\([^)]*\)\s*\{` 或函数声明模式
   - Python：匹配 `^def (\w+)\(` 或 `^class (\w+)`
   - 其他语言同理

4. **对每个功能变更进行总结**：
   - 变更类型（新增/修改/删除/重构/修复）
   - 涉及的文件路径
   - 涉及的函数名
   - 变更概述（用中文描述，1-3句话）

### 第六步：生成报告

## 注意事项

1. **大文件处理**：如果某个文件差异过大（>500行diff），使用 Read 分段读取关键部分，不要在报告中贴完整 diff
2. **二进制文件**：遇到 .bin/.elf/.o 等二进制文件，只记录"文件不同"，不分析内容
3. **超时处理**：如果文件数量超过100个，先展示摘要再逐模块深入
4. **路径格式**：Windows 路径在报告中统一使用 `/` 分隔符，避免转义问题
5. **中文输出**：所有分析描述使用中文
